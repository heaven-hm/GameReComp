### 1. README's explanation of the launch failures is contradicted by the recorded evidence

**Claim (README.md:56–61):** "The rebuilt binaries reach dynamic linking and then abort inside Homebrew
freetype 2.15.0 (`Symbol not found: _HVF_clear_part_cache` …). That is a host toolchain fault, not game
code; until the host library is fixed the honest verification status is `launch-failed`."

**Method:** search the whole repo for the claimed dyld failure; read the recorded run record and stderr
log of the launch-failed rows; read the code that assigns `boot-failed`/`launch-failed`.

**Commands and observed output**

```
$ grep -rn "dyld\|Symbol not found" projects/*/logs/*.log
projects/ikachan/logs/run.log:1:dyld[25422]: Symbol not found: _HVF_clear_part_cache
$ ls -la projects/ikachan/logs/run.log          # 2026-10-29 23:10  (stale)
$ grep -rn "libhvf\|HVF_clear_part_cache" --include=*.log --include=*.json --include=*.md . \
    | grep -v reports/audit
projects/ikachan/logs/run.log:1:dyld[25422]: Symbol not found: _HVF_clear_part_cache
  # the only other "freetype" hits are SDL2_CFLAGS lines in projects/*/build/CMakeCache.txt
$ cat projects/rrootage/logs/run.stderr.log
[pe] /Users/haseeb-mir/Downloads/recomp-apps/games/rrootage/rr.exe mapped at 0x00400000, span 0xD6000
[pe] unresolved import GLU32.DLL!gluBuild2DMipmaps
[pe] unresolved import GLU32.DLL!gluLookAt
[pe] unresolved import KERNEL32.dll!AddAtomA
[pe] unresolved import msvcrt.dll!_fdopen
...
$ python3 -m json.tool projects/cavestory-doukutsu/reports/run.json | grep -E '"status"|exit_code|unresolved_import_count'
"status": "boot-failed",  "exit_code": 2,  "unresolved_import_count": 6
```

Every one of the 14 launch-failed rows records `boot-failed`, `exit_code: 2`, and a named unresolved
import list. `tools/autorecomp/pipeline.py:499–500` defines that state —
`elif rc == 2 and "unresolved imports" in output: status = "boot-failed"` — and
`projects/ikachan/src/runtime/win32hle/host.c:56–68` returns 2 when the strict bind leaves imports
unresolved (`recomp_host_boot` → `boot(path, hle_resolve) ? 2 : 0`). A dyld abort cannot produce exit 2
with a `[host] … booted: entry …` line, because it happens before `main`. The repo's own
`docs/RUNTIME_COMPAT.md:60–66` states the correct semantics (`2` = boot failed: unresolved imports;
`-6/SIGABRT` = the dyld case) and `:91` says the pre-fix runs "keep exit code -6" — none of the 14
recorded rows is -6.

**Verdict: REFUTED.** The launch failures are the HLE layer's own missing imports, not a host toolchain
fault.

**Severity: High.** It reattributes a product gap to the environment and implies the 85/100 rows would
run once Homebrew is fixed; they would still exit 2 on the same imports.

**What would change my verdict:** a run log for one of the 14 rows showing exit `-6`/SIGABRT with the
`_HVF_` dyld error, or a build of those binaries whose imports all resolve (0 unresolved) followed by a
dyld abort.

The manifest is **internally self-consistent** — recomputing `sha256("".join(f"{sha}  {path}\n"))`

- **Nothing delivered is tracked.** Generated source, vendored runtime copies, `manifest.json`,
  `projects/*/reports/*.json` and the `table.md` evidence links all live under the ignored `projects/`
  tree (`.gitignore:50`, `git ls-files projects` → 0). The branch history contains none of it; a fresh
  clone has no deliverable and no way to audit one. Anyone (as happened at 08:54:59) can change a
  delivered project with no VCS record.
- **The digest does not cover the build configuration.** `_source_files()` walks `src/` only
  (`pipeline.py:86–99`), so `CMakeLists.txt` — which chooses the sources and the linked libraries —
  is outside `source_digest_sha256`. A change that adds a source file or a `target_link_libraries`
  entry is invisible to the digest.

**Verdict: CONFIRMED** (gap). The manifest was a correct binding at 08:46; it is stale at 08:56.

**Severity: High** against a "provenance for every delivered line" anti-claim.

**What would change my verdict:** `projects/` un-ignored (or a tracked `projects.lock.json` carrying the
same hashes), `CMakeLists.txt` and the toolchain/link line inside the digest, and a re-generated
manifest whose digest matches the tree at the commit being reviewed.

### 4. Dummy-success shim on the delivered path: accelerators are fabricated, not implemented

**Claim:** no dummy-success Win32 shim stands in for an API whose result the guest depends on.

**Method:** enumerate every shim body in the delivered runtime (747 `void name(void)` bodies scanned;
the scan prints every body that makes no call and returns a constant success — ~90 of them, listed in
finding 5), then filter by (a) registration in the shim table, (b) preprocessor branch actually
compiled, (c) whether the original PE imports the name.

**Commands and observed output**

```
$ r2 -q -c "ii" /Users/haseeb-mir/Downloads/recomp-apps/games/ikachan/dxIka.exe | grep -E "Accelerator|Heap"
14  0x00411160 NONE FUNC USER32.dll   LoadAcceleratorsA
5   0x0041113c NONE FUNC USER32.dll   TranslateAcceleratorA
46  0x004110f4 NONE FUNC KERNEL32.dll HeapCreate
56  0x0041111c NONE FUNC KERNEL32.dll HeapDestroy
```

```
projects/ikachan/src/runtime/win32hle/user32.c:2114
static void u_LoadAcceleratorsA(void){ RET(0x1C000005u, 2); }  /* nonzero: games treat NULL as fatal */
projects/ikachan/src/runtime/win32hle/user32.c:1967
static void u_TranslateAcceleratorA(void) { RET(0, 3); }
```

`dxIka.exe` imports both; the strict bind recorded 0 unresolved, and `hle_resolve` matches by name, so
these two shims are the binding targets. The guest receives a **non-zero HACCEL that owns no accelerator
table** (so it takes the "success" path) and then `TranslateAcceleratorA` returns 0 forever: every
keyboard accelerator in the game is silently dead. The comment states the fabrication is deliberate to
avoid a NULL-fatal path — i.e. a fake success chosen over a fail-closed one. It is disclosed nowhere in
`README.md`, `docs/RUNTIME_COMPAT.md` or `docs/VERIFICATION.md`.

**Verdict: CONFIRMED** — a live dummy-success shim whose result the guest depends on.

**Severity: High** for the shim-honesty anti-claim (medium for gameplay impact).

**What would change my verdict:** `LoadAcceleratorsA` parsing the ACCELERATOR resource and
`TranslateAcceleratorA` dispatching it (with a test), or the pair replaced by a fail-closed refusal, or
an explicit disclosure in `docs/RUNTIME_COMPAT.md` that accelerators are non-functional.

### 5. Other shims that return success without doing the work

**Claim:** outside finding 4, no other shim returns success, TRUE or a handle for work the guest then
depends on.

**Method:** as in finding 4, then each candidate read in full and classified. Enumeration below is the
complete set of constant-success bodies that are *reachable*; the negative results matter as much as
the positives.

**Live, on the delivered path (imported by `dxIka.exe`)**

| file:line | shim | what it does | judged |
|---|---|---|---|
| `kernel32.c:153` | `HeapCreate` → `1` | returns the *process-heap pseudo-handle* for a private heap that is never created; the handle is then ignored by `HeapAlloc/HeapFree` (they use one global block table) | **fake-ish but functionally survivable**; `HeapDestroy` (`:154`) returns TRUE and frees nothing → leak |
| `kernel32_crt.c:86–90` | `GetStdHandle`/`SetStdHandle` | `SetStdHandle` returns TRUE and stores nothing; `GetStdHandle` returns fixed `0x11/0x12/0x13` | **fake** but harmless for a GUI game |
| `kernel32.c:231` | `VirtualProtect` → TRUE, old-protect `PAGE_READWRITE` | no-op; lies about the previous protection. Not imported by `dxIka` | honest given no execute permission exists, but the out-value is fabricated |

**Live, not imported by `dxIka` (fake for any project that imports them)**

- `winmm.c:105–119` `waveOutOpen` returns `MMSYSERR_NOERROR` with a fabricated `HWAVEOUT 0x5A5E0001`,
  and `waveOutWrite` immediately sets `WHDR_DONE|~WHDR_INQUEUE` — "a silent device that retires every
  buffer at once". A guest mixer believes playback completes instantly; audio is silently absent.
  `waveOutGetNumDevs` reports 1. `runtime/win32hle/README.md:70` mentions "no mixer", but the fabricated
  handle/completion is not disclosed as a dummy success.
- `advapi32.c:230` `InitCommonControlsEx` → 1 (harmless), `bink.c:36` `BinkSetSoundSystem` → 1 (the
  sound system is never set), `mss.c:26` `AIL_startup` → 1 (no global state to initialise; the real
  file/decoder helpers are implemented).
- `ddraw.c`/`dsound.c` no-op `DD_OK`/`DS_OK` methods (`dd_Initialize:296`, `dd_RestoreDisplayMode:297`,
  `sf_Initialize:528`, `pl_Initialize:609`, `cl_SetClipList:614`, `d_SetCooperativeLevel:396`,
  `d_Compact:397`, `d_Initialize:400`, `b_Unlock:278`, `b_Restore:335`, …). These are the "method exists,
  does nothing" class. They are individually defensible for a 2-D presenter, but they are a large
  surface of success returns; none is listed as a known gap in the docs.

**Candidates that are NOT live (checked, negative result — do not report these as fakes)**

- `gdi32.c:112–113` `g_CreateCompatibleDC` → constant `0x0DC00002` and `g_DeleteDC` → 1 look like the
  worst offender (a fake HDC). They are **dead**: `gdi32.c:138–143` no longer registers either name
  (`/* CreateCompatibleDC/DeleteDC now in gdidc.c */`), and nothing else references them
  (`grep -rn g_CreateCompatibleDC projects/ikachan/src/runtime/win32hle/` → only the unregistered
  definitions in `gdi32.c:112–113` and the registered ones in `gdidc.c:839,848`).
  The live pair is `gdidc.c:839–840` (`new_dc()` / `hle_gdi_release_dc`).
- `bink.c` and `mss.c` `k_ret0_*` / `r_request_interface` stubs are inside `#ifndef HLE_WITH_FFMPEG`;
  the delivered build defines `HLE_WITH_FFMPEG` (`build/CMakeFiles/dxIka.dir/flags.make`:
  `C_DEFINES = -DHLE_WITH_FFMPEG`; `nm -u dxIka | grep -c '^_av'` → 25), so the FFmpeg implementations
  are the ones compiled.
- `s_ShellExecuteA` returns 31 (`advapi32.c:249`) — 31 is *below* the ShellExecute success threshold
  (32), i.e. an honest failure with a printed reason, not a fake success.
- `k_CreateProcessA` (`kernel32.c:94–98`) returns 0 with last-error 2 and prints "not on this host" —
  honest failure. (`GetExitCodeProcess` → TRUE/0 at `:120` is therefore unreachable in practice; not
  imported by `dxIka`.)
- `k_UnhandledExceptionFilter` → 0 (`EXCEPTION_CONTINUE_SEARCH`), `k_FlushInstructionCache` → TRUE,
  `k_HeapValidate` → TRUE, `k_SetHandleCount` → its argument: no-ops where Windows' own answer is
  meaningless here.

**Verdict: CONFIRMED (mixed)** — two live fakes that matter (`LoadAcceleratorsA`/`TranslateAcceleratorA`
in finding 4, `HeapCreate`/`HeapDestroy`), one live fake class off the delivered path (`waveOut*`), and a
larger set of honest no-ops. No case was found where a *critical* API returns success for work the guest
then observes as done (no fabricated file handles, no fabricated DirectDraw surface, no fabricated
decoder).

**Severity: Medium.**

**What would change my verdict:** a call trace showing the no-op `DD_OK`/`DS_OK` methods are depended on
for observable output, or finding a shim that hands out a handle the guest dereferences into
uninitialised state. To make `waveOut` honest, either implement it on the SDL audio path or return
`MMSYSERR_NOTENABLED`.

### 6. A binary that never boots scores 85/100

**Claim (table.md):** `PASS /100` is weighted stage completion; "A stage only counts when it succeeded

**Method:** read `stage_run`/`stage_verify`/`score` and confirm the arithmetic against the recorded 85s.

```

        # A boot failure is a classified outcome, not a stage error: verify
        # grades it as launch-failed, so it must not cost the run stage its
        # points as well.
```

"is not a measure of game equivalence" — but `README.md:52` presents 75/100 (and the true 85) with no

**Severity: Medium** (misleading rather than false).

**What would change my verdict:** a score cap for `launch-failed`/`not-run` rows, or a README that prints

**Mechanism, stated exactly:** every guest transfer is a C call into the generated dispatch table.
Direct calls are `RECOMP_CALL`; indirect calls/tail jumps are `RECOMP_ICALL`/`RECOMP_ITAIL`, which resolve
through `recomp_lookup` (482-entry binary search over `recomp_dispatch_table`, `recomp_dispatch.c`) or
`recomp_lookup_import` (synthetic shim VAs), and on failure print the VA and zero `eax` rather than
calling it. Guest memory is reserved `PROT_NONE` and committed `PROT_READ|PROT_WRITE` only
(`guest_mem.c:104,111,125,167`); there is no `PROT_EXEC` anywhere in the delivered runtime, including the
file-mapping path (`kernel32_ext.c:757`: `PROT_READ|PROT_WRITE` at most). The PE is read for its
headers, sections, resources and IAT only (`pe_loader.c:84–106`). Running the binary confirms the guest's
lifted code executes and the PE is never called into: stderr is the PE map line, the bind line, the boot
line, then `[win32hle] ExitProcess(1)`.

**Verdict: CONFIRMED** (the anti-claim holds for the delivered artifact).

**Severity: n/a (clean).**

**What would change my verdict:** any `PROT_EXEC`/`PAGE_EXECUTE*` in a compiled runtime source, a
`recomp_lookup*` implementation that returns a pointer into the mapped image, or an unresolved-ICALL path
that jumps to the raw VA.
