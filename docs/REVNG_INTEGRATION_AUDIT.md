# rev.ng / Anvill / Remill / Rellic integration audit (issue #4)

This audit answers issue #4's question about reusing the rev.ng family for
GameReComp. It is a **read-only upstream survey plus a real detection probe**:
`tools/revng_probe.py` reports which binaries are reachable on this host and
why the rest are not. No upstream source was cloned into the tree, no upstream
code was copied, no licence text was vendored, and **no decompiler was run**.
A probe result is a detection result, never a fidelity or integration claim.

Survey date: 2026-11-23. Method: `webfetch` of the public GitHub repository
pages and `raw.githubusercontent.com` README/LICENSE files (no `git clone` of
the large trees). The GitHub REST API returned HTTP 403 (rate limit) during
the survey, so branch names and licence badges are taken from the rendered
repository pages, and licence texts from the checked-in `LICENSE` files where
available.

### Licence details that matter for adoption

- **rev.ng** README: "rev.ng depends on certain on GPLv2 components (in
  particular, QEMU), so the project is GPLv2-licensed as a whole. However, the
  individual files are licensed under the MIT license." GitHub reports
  "GPL-2.0, MIT licenses found". Read that as GPLv2 for any combined
  distribution; the per-file MIT grant does not relicense the whole.
- **Anvill** is **AGPL-3.0**, not Apache. AGPL §13 extends copyleft to
  network users of a modified service. That is a materially different
  obligation from the Apache-2.0 Remill/Rellic stack it sits on, and it is the
  strongest copyleft in this family.
- **Remill**'s `LICENSE` is the verbatim Apache License 2.0 (checked). It is a
  permissive licence, but Remill is consumed as a CMake library, so linking it
  into a distributed binary still brings Apache §4 attribution/NOTICE duties.
- **Rellic** declares Apache-2.0 and depends on LLVM 16 and Z3 4.7.1+.
- **LLVM** is Apache-2.0 with the LLVM Exception; the system `objdump` is
  binutils (GPL), which is another reason to keep these as external tools
  rather than embedding them.

## Findings per tool

### rev.ng — full decompiler, but GPLv2 and Linux-only natively

The framework is LLVM + QEMU based and ships a real decompiler. Its own
integration guide in this repo (`tools/autorecomp/revng.py`) records measured
output on an i386 PE32 fixture: it recovered the Microsoft x86 cdecl calling
convention, named a function from its address, resolved an import by name and
recovered a local. That is structural ground truth, but the emitted names
(`generic32_t`, `var_0`, `function_0x401000_Code_x86`) are mechanical — rev.ng
supplies structure, not readability. Its PTML markup carries token-to-
instruction provenance, which is useful for later renaming proofs.

Two hard constraints: upstream runs on Linux x86-64, so on this macOS host it
is only reachable through the `revng/revng` container under an emulated
platform; and the project as a whole is GPLv2. In-project mode the C body and
the type/helper headers must come from the same cached `.revng-project` model,
otherwise recovered struct/union numbering diverges and produces plausible
wrong offsets.

### Anvill — useful lifting, but AGPL-3.0 plus a closed-source dependency

Anvill generates high-quality LLVM bitcode from raw machine code using Remill,
intended to be decompiled further by Rellic. Its README states that **the
`master` branch consumes protobuf specifications generated by an
in-development, closed-source Ghidra plugin**; the `binja-final-version` tag
has an open-source specification generator using Binary Ninja. That means the
default branch of an AGPL-3.0 project has an unavailable input path — a
reproducibility problem before any licence question is even reached. Another
documented tool, `anvill-specify-bitcode`, is marked "currently unsupported".

### Remill — lifter library, no PATH-visible CLI by default

Remill translates x86/amd64, AArch64 and SPARC instructions to LLVM bitcode
and is designed as a library for other tools. It needs LLVM 15+, Clang 15+,
Intel XED, glog and gtest; Linux (Ubuntu 22.04) is tested, macOS works, Windows
is experimental. Because it is a CMake library, **absence of a `remill` binary
on PATH does not prove Remill is absent** — check
`<prefix>/lib/cmake/remill` separately. The probe records that as an explicit
limitation rather than reporting a false negative.

### Rellic — C emitter with a strict LLVM version coupling

Rellic implements pattern-independent structuring to emit goto-free C from
LLVM bitcode, interoperating with Remill. It requires LLVM 16 and Z3 4.7.1+,
is tested on Ubuntu 22.04, and names its tools `rellic-decomp`,
`rellic-headergen` and `rellic-xref`. Bitcode must be produced by the matching
LLVM version or the decompilation is meaningless — a version pin, not just a
binary, is part of any real integration.

### LLVM utilities — present, but not decompilers

Disassemblers and bitcode utilities are supporting infrastructure only. Their
presence says nothing about whether any of the four decompilers are installed
or whether their IR versions match.

## The probe (`tools/revng_probe.py`)

A small, real, machine-readable detector. It reads the environment only,
never executes a tool, and never imports or vendors upstream code.

```sh
python3 -m tools.revng_probe                      # JSON on stdout
python3 -m tools.revng_probe --out report.json    # write to file
python3 -m tools.revng_probe --compact            # one line
python3 -m tools.revng_probe --tools-file extras.json
python3 -m tools.revng_probe --path /custom/bin:/usr/bin
```

`--tools-file` accepts a JSON **list**. A bare string adds an extra binary to
the `user-supplied` group; an object can define a full group:

```json
[
  "ghidra",
  {
    "tool": "ghidra",
    "binaries": ["analyzeHeadless"],
    "primary": "analyzeHeadless",
    "env_var": "GHIDRA_BIN",
    "licence": "Apache-2.0"
  }
]
```

Report shape (`schema_version: 1`, key-sorted JSON):

- `tools.<name>.status` — `available` (primary binary found), `partial` (only
  secondary binaries found), or `missing`.
- `tools.<name>.found` / `.missing` — binary names with resolved paths and
  detection source (`path` or `env`).
- `tools.<name>.reason` — an explicit, human-readable reason for the status,
  including what was expected and the upstream caveat.
- `tools.<name>.upstream` / `.licence` / `.role` — recorded facts, not verdicts.
- `summary.overall`, `.available_core_tools`, `.feasible_pipelines`,
  `.pipelines` — which of `revng-decompilation`, `remill-rellic-lifting`,
  `anvill-specification-lifting`, `llvm-utility-support` are reachable.
- `limitations` — what the probe does not prove.

Exit status is 0 for a successful probe and 2 for a malformed tools file. Tool
absence is data in the JSON, not a process failure.

Tests: `python3 -m pytest tests/test_revng_probe.py -q`. They mock PATH with a
temporary directory of executable stubs and patch `shutil.which`, so they are
deterministic and never touch a real toolchain.

## 为什么不盲目集成 (Why not integrate blindly)

1. **许可证不兼容 (Licence incompatibility).** rev.ng is GPLv2 as a whole via
   QEMU; Anvill is AGPL-3.0 with a network-use clause. Linking either into a
   distributed DLL-style pipeline would impose copyleft obligations. They must
   stay external processes/containers with clearly separated boundaries, and
   even then the terms must be reviewed before redistribution. Remill/Rellic
   are Apache-2.0, but still carry attribution duties.
2. **不可复现的输入 (Unavailable input path).** Anvill's default branch needs
   protobuf specs from a closed-source Ghidra plugin. A toolchain whose main
   branch cannot generate its own inputs is not a safe build dependency.
3. **本机不可用 (Not installed here).** None of the four tools is on PATH on
   this host. A hard dependency would break the verified build and test
   workflow; the probe exists precisely so this is detected rather than
   assumed.
4. **平台和构建负担 (Platform and build burden).** Remill needs LLVM 15+ and
   Intel XED; Rellic needs LLVM 16 and Z3; Anvill needs Remill, LLVM 12+ and
   Ghidra; rev.ng needs a Linux x86-64 host or an emulated container. The repo
   builds Windows x86 DLLs — none of these is a drop-in win32 toolchain.
5. **语义鸿沟 (Semantic gap).** These lifters model native ISA instructions and
   emit generic C with raw memory accesses. They do not model the Win32 PE32
   environment, imports, DirectX shims or the game ABI that GameReComp
   reimplements. Mechanical names are structure, not readable source; a
   deterministic renaming/structuring layer is still required.
6. **保真度未证 (Fidelity unproven).** Tool output changes with versions, and
   the project's own rules require evidence before behaviour-changing work:
   validate in the harness first, keep native wrappers typed, and never claim
   live-game success from a build or emulator result alone. A "we integrated
   rev.ng" claim without a pinned version and a fixture parity check would be
   exactly the unsupported claim this audit rejects.

### Recommendation

Keep this probe as an advisory detector. If a real provider is ever wanted,
expose it behind an opt-in path/container setting, pin exact upstream commits
and LLVM versions, review GPLv2/AGPL-3.0 with the project's licence policy,
prove parity on a checked-in fixture in the harness, and only then consider
calling it from the game-thread runtime path. Do not vendor the sources, do
not link the GPL/AGPL components, and do not treat a probe hit as evidence of
correct decompilation.
