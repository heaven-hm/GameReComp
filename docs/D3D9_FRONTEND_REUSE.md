# Direct3D 9 guest COM frontend — ABI provenance

## What was implemented

- `runtime/win32hle/d3d9.c`: a guest-facing `d3d9.dll` frontend that serves
  `Direct3DCreate9`, an `IDirect3D9` object (17 vtable entries) and an
  `IDirect3DDevice9` object (119 vtable entries), with real IUnknown reference
  counting, IID identity checks and `E_POINTER`/`E_NOINTERFACE`/`D3D_OK` HRESULTs.
- Adapter count, adapter mode count, mode enumeration and display mode queries
  read the **shared** display mode through `hle_dd_mode()`; no second renderer
  or host GL context is created.
- Methods requiring a rasteriser (resource creation, state, draws, shaders,
  presentation) return `D3DERR_NOTAVAILABLE` with their real stdcall argument
  count. There are no fake-success COM objects.
- `runtime/win32hle/d3d9_selftest.c`: drives the public vtables slot by slot,
  checks all 17 + 119 entries, IUnknown identity, invalid IIDs, NULL pointers,
  adapter queries, device creation, refcount destruction and honest failures.

## Upstream reuse

- Repository: `wine-mirror/wine`, commit
  `97027f879ba9a36dbe594720d4710818536e5433`.
- Exact file read: `include/d3d9.h` (Wine's public DirectX 9 header).
- Reused: the **method names, declaration order and parameter counts** of
  `IDirect3D9` (17 entries) and `IDirect3DDevice9` (119 entries). These define
  the guest vtable layout and the stdcall stack purge, which must match the
  Windows ABI exactly.
- Not copied: no Wine C/C++ source was copied. The C shim file was written
  fresh in the style of GameReComp's existing `d3d8.c`/`ole32.c` frontend.
- Licensing: method names/order are public interface facts. Implementation is
  original GameReComp code, so no LGPL obligations arise from this file.
- The layout was generated by a local script that parses the header; the
  generated table is checked into `d3d9.c` so builds have no network or Wine
  dependency.

## Architecture compliance

- Extends the existing win32hle layer; no new runtime, renderer, loader or GUI.
- Uses the shared `hle_com_vtable`/`hle_com_new`/`hle_com_free` helpers in
  `ole32.c` and the shared display mode in `ddraw.c`/`d3d7.c`.
- Method shim names are namespaced (`D3D9::Object::…`, `D3D9::Device::…`) so
  registering this module cannot collide with D3D8's `IDirect3D8::…` entries.

## Honest limitations

- No rasterisation: `CreateDevice` yields a COM object whose rendering methods
  all return `D3DERR_NOTAVAILABLE`. No game can render through this frontend.
- No D3D9Ex, swap chains, textures, shaders, state blocks, queries or present.
- No real-game validation was performed in this change; only ABI/selftest
  evidence exists. Linux host execution remains unavailable on this machine.
