# Proof evidence: frames and Unicorn reference execution

This document records exactly what was verified, and what was **not**, for the
request for side-by-side Windows/native screenshots and Unicorn memory
comparison.

## 1. Native frame proof (no Windows oracle column)

`tools/frame_proof` decodes the runtime's uncompressed 24-bpp BMP captures,
counts distinct RGB colours and hashes each file. Output:
`test-results/game-matrix/frame-proof/frame-proof.json` and a side-by-side
gallery `native-frames.html` (both gitignored, regenerated by the command
below).

```
python3 -m tools.frame_proof \
  --summary test-results/game-matrix/execution/summary.json \
  --out test-results/game-matrix/frame-proof
```

Measured result from the final all-games run:

| Game | Frames | Distinct colours | Honest verdict |
|---|---|---|---|
| Cave Story | 3 × 640×480 | 1, 5, 3 | frame 0 blank; frames 1–2 have real content but only 3–5 colours |
| Ikachan | 3 × 351×238 | 1, 1, 1 | **all blank**; a longer 20 s / 10-frame run also produced 10 blank frames |
| OUCC Tetris | 3 × 310×418 | 4, 5, 5 | non-blank; boot + some rendering, not gameplay |

A single-colour frame is flagged `blank: true` and is **not** counted as
graphics evidence. The earlier claim that Ikachan "rendered frames" was based
on frame files existing; this colour check corrects it.

The gallery intentionally has **no Windows-original column**: there is no
original-Windows execution oracle in this environment, and Wine is not used as
the final runtime. A Wine-captured frame would not be a Windows oracle anyway.

## 2. Unicorn reference execution (function-level, not whole-game)

`tools/lift/difftest.py --project` runs the ORIGINAL PE bytes under Unicorn
from the same entry state as the project's generated C, then compares the
eight general-purpose registers, named EFLAGS and every byte of named guest
memory. Its own report states that this proves nothing about other addresses,
other input sets, or the game as a whole.

Run on the rebuilt OUCC Tetris project against the original PE
(SHA-256 `024dccd5e227ac4bfcf698e948b1682c4a42ddadde87ec5f18193ee16ca77b8d`):

- **`0x00406370`: `agree` — 0/4 cases differ, 1 named address** (`test-results/unicorn-tetris-leaves.json`). This is a real, measured memory/register equivalence between the original bytes and the generated C for that function and those four inputs.
- Five other candidate addresses were **not** reported as agrees: four were `original-faulted` because their synthetic entry state calls an unresolved import in the reference machine, and one had no generated body. The entry point `0x004013D0` also faulted in Unicorn. These are refusals/faults, not passes and not proof of divergence in the lift.
- The existing repository report `reports/per-function-oracle.md` documents the same method on IGI/Ikachan with an `agree` case.

## 3. Memory equivalence — exact scope

For `0x00406370` and the four driven cases, the compared state is: EAX/ECX/EDX/EBX/ESI/EDI/EBP/ESP, named EFLAGS bits, and the bytes of the one absolute guest address the generated body names. That is the measured equivalence. It does **not** establish whole-process memory equality, side-by-side full-game behaviour, or A10 original-vs-native acceptance.

## 4. What is still missing for the requested side-by-side

1. A legal original-Windows runtime and the original game for each title (not available here).
2. A stable per-game capture oracle (identical input recording, frame timing and display mode on both sides).
3. Enough non-blank native frames to compare (Ikachan currently produces none).

No claim beyond the measured statements above is made, and no issue was closed.
