## Acceptance gate definitions (A0–A10)

Derived from `docs/GAME_MATRIX_METHODOLOGY.md` ("Acceptance mapping") and the
per-game columns in the `docs/GAME_MATRIX.md` Agent 3 addendum. A gate is
"met" only when evidence is committed or referenced by path/hash; a bare
compile, a bare process exit, or an upstream `†` claim never satisfies a gate.

| Gate | Name | Evidence required |
|---|---|---|
| A0 | Inspect | Input identity: PE32 x86 detection from the file bytes and SHA-256 keying. |
| A1 | Recover | Function recovery stage result (functions recovered). |
| A2 | Translate + project | Generated C and project creation stage result. |
| A3 | Compile | Native build stage result (rebuilt binary produced). |
| A4 | Runtime | Process launches and stays alive (or exits cleanly) in the run stage. |
| A5 | Menu | Menu is reached and renders. |
| A6 | Graphics | Graphics/frame evidence (renderer output). |
| A7 | Input | Input/controls verified with an independent scenario. |
| A8 | Audio | Audio verified with a real output path (a dummy device is only PARTIAL). |
| A9 | Save/load | Persistence (save/load) verified with a scenario. |
| A10 | Original-vs-native comparison | Differential comparison against an original Windows oracle. |

A0–A3 are stage/build results; A4 is process-level only; A5–A10 require
independent scenario evidence. "PARTIAL", "NOT TESTED", "BLOCKED" and
"UNTESTABLE" are never PASS.

## Limitations

1. **Evidence is quoted, not re-verified.** Commit hashes, branches, test
   counts and game verdicts are copied verbatim from the two source documents.
   Abbreviated hashes (`46dc1ce`, `6fb3bb44…`, `90a80cee…`, etc.) are preserved
   as abbreviated; they were not expanded or confirmed to exist on a remote.
   Full 40-hex hashes in the plan are likewise quoted, not independently
   fetched. Build/test counts are session claims, not reproduced here.
2. **Source documents disagree on #22/#23.** The execution plan says a Windows
   PE32 binary was found, hashed and is building; the GAME_MATRIX addendum says
   BLOCKED with only a native macOS app present. Neither document quotes the
   SHA-256. The ledger records both claims verbatim and does not resolve the
   conflict; A0 is therefore at most PARTIAL for those two games.
3. **Plan statuses are not GitHub states.** Labels such as PARTIALLY VERIFIED,
   BLOCKED, DEFERRED and IN_PROGRESS come from the execution plan. The only
   live GitHub fact verified here is that all issues are OPEN with no closure.
4. **Game evidence paths are gitignored.** `test-results/<game>/` directories
   are gitignored per the integration checkpoints; only the referenced summary
   text and the IGI SHA-256 are committed in the source docs. Raw frames, logs
   and reports were not inspected for this ledger.
5. **A0–A10 mapping is interpretive.** The stage→level grouping and the
   A5–A10 names (menu, graphics, input, audio, save/load, oracle) follow
   `docs/GAME_MATRIX_METHODOLOGY.md` and the addendum columns, but no canonical
   machine-readable mapping existed before `tools/acceptance_schema.json`.
6. **No game or live injection was run.** This is a documentation-only task;
   no DLL, game binary or original Windows file was executed. No issue is
   closed or marked complete as a result of this ledger.
